# Automatic Prisma deployment and ownership migration

Configured in the repository; no deployment or remote database migration was performed for this change.

## Deployment path

```text
Git push to Render's linked branch
  -> Render builds Dockerfile
  -> Backend build: prisma generate && tsc -p tsconfig.build.json
  -> Container: npm --prefix Backend run start:production
  -> npm run db:migrate (prisma migrate deploy)
  -> npm start (node dist/src/server.js), only if migration succeeded
```

`Backend/package.json` defines `start:production` as `npm run db:migrate && npm start`. Docker's CMD and Render's `dockerCommand` both call it. Prisma is already a production dependency, and the runtime image copies the schema and migration directory. Nothing runs a migration during image build. Local `dev` and plain `start` remain unchanged.

The Blueprint retains the free Docker plan and sets `autoDeployTrigger: commit`. [Render pre-deploy commands](https://render.com/docs/deploys#pre-deploy-command) are only available on paid web services, so this service uses a startup gate rather than adding an unsupported pre-deploy hook. An unsuccessful migration exits nonzero and the new API never starts listening. Prisma's migration history prevents successful migrations from running again on subsequent starts, and its advisory locking coordinates concurrent migration processes. Lock contention or a failed migration fails startup; errors are not ignored.

## One-time Render setup

Before the next deployment, sync the updated Blueprint. If the existing service is not Blueprint-managed, configure its Docker Command as `npm --prefix Backend run start:production` and Auto-Deploy as On Commit. Repository changes alone cannot update a manually managed Dashboard service. No Render settings were changed remotely in this task because deployment was not authorized.

Set `DIRECT_URL` securely on Render if missing: use the Supabase direct PostgreSQL endpoint or session pooler on port 5432, with migration privileges. Keep `DATABASE_URL` for runtime access; both URLs must reference the same database/schema. `sync: false` does not store a secret in Git and does not necessarily prompt for a newly added secret when updating an existing Blueprint. Verify the Dashboard value once. Do not use a transaction pooler on port 6543 for this migration connection. No authentication, RLS grants, or Supabase settings need to be weakened.

Once connected to this pipeline, routine deployments need no manual database edits or migration invocation. Commit new migrations with future schema changes. This setup never invokes `db push`, `migrate dev`, resets, or seeds in production.

## Pending ownership migration

`20260914120000_group_ownership` is corrected in place because it has not been applied to Supabase. Do not edit this file after it is deployed; future changes need a new Prisma migration.

The migration:

- Uses an explicit transaction with a 15-second lock timeout and 120-second statement timeout. A failed statement rolls back the ownership column, backfill, constraint, and key changes together.
- Adds nullable `Conversation.ownerId` with a foreign key to `User`. Existing direct conversations stay NULL. Idea-group owners come from the idea author. For deleted ideas, the initial system-message sender is used if available. Unrecoverable ownership stays NULL instead of guessing an administrator or deleting data; existing backend admin checks deny unauthorized administration.
- Retains an already-valid canonical group when one exists. Otherwise the oldest group per idea wins, with ID as a tie-breaker. Its unique key becomes `idea:<ideaId>`.
- Keeps all duplicate groups and their histories. An unrelated legacy group occupying a reserved canonical key is given a collision-free `legacy:<conversationId>` key; its ID, idea relationship, membership, messages, name, and timestamps do not change.
- Leaves existing unique, kind-integrity, foreign-key and RLS protections in place. No group or member model is replaced.

The read-only Supabase audit found two groups for idea `cmtzwimbe000vds2du2s98muv`:

| Group | Members | Messages | Result |
| --- | ---: | ---: | --- |
| `cmu04u0ju004jil1vfnlhbl2x` | 3 | 2 | Oldest, becomes canonical |
| `cmu06m6p60061il1voj6z8jef` | 2 | 1 | Preserved legacy group |

Both contain their idea author as an active member. No merge, deletion, or membership transfer is performed. The existing group service uses the unique idea-only key and Serializable retries for future creation/join requests. Legacy duplicates intentionally remain associated with the idea, so a global unique index on `ideaId` is not appropriate.

For this first transition, ensure the old membership-key-based group creator is not serving writes while switching to the new version (a brief maintenance window for the initial rollout is sufficient). An old application instance can otherwise create a legacy-key group after the migration commits. Future migrations should remain compatible with old and new application versions during Render's rolling deployments; automatic migrations do not make destructive schema changes safe by themselves.

The connection-list fix remains `conversation: { select: { id: true } }`. Connection listing does not require the ownership migration, although the group features do.

## Failure handling

Do not bypass the startup gate or manually mark a failed migration applied to get a deploy live. Inspect the error and fix its cause. Prisma can retain a failed migration entry even though this transactional SQL rolled back. After verifying rollback and correcting the cause, an operator may use Prisma's supported `migrate resolve --rolled-back` recovery for that failed entry, then redeploy. This is exceptional failure recovery, not a normal per-deployment database-edit step. Never automate dismissal of migration failures.

## Verification

Use the existing dedicated local PostgreSQL helper, not remote credentials:

```sh
node Backend/scripts/group-test-db.mjs
```

In another terminal at the repository root:

```sh
node Backend/scripts/run-group-check.mjs Backend/node_modules/prisma/build/index.js validate --schema Backend/prisma/schema.prisma
npm --prefix Backend run db:generate
node Backend/scripts/run-group-check.mjs Backend/scripts/group-migration-check.mjs
node Backend/scripts/run-group-check.mjs Backend/scripts/deployment-migration-check.mjs
node Backend/scripts/run-group-check.mjs --import tsx --test --test-concurrency=1 Backend/tests/*.test.ts
npm --prefix Backend run typecheck
npm --prefix Backend run lint
npm --prefix Backend run build
```

The existing group regression database must already have its schema (for a fresh local installation, apply migrations to it through `run-group-check.mjs` and the Prisma CLI). This helper overrides database, email, and storage settings for child processes. Tests create/remove only local fixtures. Do not run the fixture-based backend suite directly against Supabase.

The migration preservation check uses session-local tables covering duplicate groups, existing canonical keys, reserved-key conflicts, NULL owners, deleted ideas, messages, departed members, and FK/unique/check constraints. It injects a failure before COMMIT and verifies complete rollback. The fresh-deployment check creates a new empty database on local port 55439, runs the real `prisma migrate deploy` twice, checks the second is a no-op, and verifies the ownership FK and RLS. It retains that isolated test database; it never resets or seeds a database.

Deployment tests execute the actual production script string in temporary npm fixtures: migration success must start the test API marker, and failure must return nonzero without creating that marker. Group tests cover creator permissions, removal/access revocation, persistent group identity and concurrent joins. The database-free connection regression covers the missing `ownerId` selection bug.

Run builds after database tests finish on Windows, because Prisma's loaded DLL can otherwise prevent generation. Docker and Render live deployment verification require those environments and were not performed as part of this local change.
